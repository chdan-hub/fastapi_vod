Spec API는 API의 기능과 동작 방식을 문서화한 명세(Specification, 분명하고 자세함)를 의미한다.
즉, 서버와 클라이언트가 어떤 요청과 응답을 주고받는지에 대해 표준화된 약속을 제공한다.
대표적으로 OpenAPI Specification (OAS) 가 널리 사용되며, FastAPI는 이를 기본적으로 지원한다.


Spec API가 왜 필요할까??
    명확한 약속을 제공한다.
        API 요청 및 응답 형식이 명확하게 정의되어 있어 개발자 간 혼선을 줄일 수 있다.
    자동 문서화 지원한다.
        별도의 문서를 작성하지 않아도 코드 기반으로 문서가 자동 생성되어 유지보수가 편리하다.
    테스트와 연동이 용이하다.
        다른 개발자나 외부 서비스가 문서를 통해 API를 쉽게 테스트하고 연동할 수 있다.


FastAPI에서 Spec API 어떻게 활용할까??
    FastAPI는 작성한 엔드포인트와 데이터 모델을 바탕으로 자동으로 OpenAPI 문서를 생성한다.
    이 문서는 웹 페이지 형태로 제공되며 다음과 같이 접근할 수 있다.

        http://127.0.0.1:8000/docs
            → Swagger UI를 통해 API를 시각적으로 확인하고 직접 테스트할 수 있는 화면 제공한다.
            /docs는 FastAPI가 자동 생성하는 API 문서 페이지로, 개발자가 만든 엔드포인트를 직접 확인하고 테스트할 수 있는 중요한 도구이다.
        http://127.0.0.1:8000/redoc
            → ReDoc을 통해 깔끔한 문서 형태로 API 스펙 제공한다.

결론
    1. Spec API는 API 동작을 표준화된 문서로 정의한 것
    2. FastAPI는 OpenAPI 기반의 Spec API를 자동 생성하여 개발자가 별도의 문서를 작성하지 않아도 됨
    3. /docs 페이지를 통해 자동 생성된 Swagger UI에서 API를 직접 확인하고 테스트할 수 있음
    4. 이를 활용하면 개발자 간 협업, 서비스 연동, 테스트 작업을 효율적으로 수행할 수 있다.

dmypy는 mypy(파이썬 타입 검사기) 를 더 빠르게 실행하기 위해 제공되는 데몬 모드 도구이다.
    데몬?? 운영체제에서 백그라운드(뒤에서 계속 실행되는 상태) 로 돌아가는 프로그램으로 사용자가 직접 실행/종료하지 않아도,
    특정 작업을 빠르게 처리하기 위해 항상 대기하는 서비스 같은 역할을 한다.

mypy는 Python 코드에서 타입 힌트가 올바르게 사용되었는지 검사하는 정적 타입 검사기인데
큰 프로젝트에서는 실행할 때마다 코드 전체를 다시 검사하기 때문에 시간이 오래 걸릴 수 있다.
    -> dmypy는 백그라운드에서 타입 검사 서버를 실행해 두고, 이후 검사 시에는 변경된 부분만 빠르게 확인할 수 있도록 해준다.
        -> mypy = 타입 힌트 검사를 하는 기본 도구
           dmypy = mypy를 더 효율적이고 빠르게 실행할 수 있게 만든 보조 도구
           즉, 코드 작성 시 타입 안정성을 지키면서도 검사 속도를 높여 개발 효율을 올려준다.


dmypy를 어떻게 활용할까??????
    서버 시작
        dmypy start
            → 타입 검사 서버를 백그라운드에서 실행

    타입 검사 실행
        dmypy check your_file.py
            → 지정한 파일을 빠르게 타입 검사

    상태 확인
        dmypy status
            → 서버가 정상적으로 실행 중인지 확인

    서버 중지
        dmypy stop
            → 더 이상 필요 없을 때 서버 종료

    예시
        def add(x: int, y: int) -> int:
            return x + y

        result = add(3, "hello")  # 타입 오류 발생
            -> 위 코드를 dmypy check example.py 로 검사하면, "hello" 가 문자열이라서 int 타입에 맞지 않는다는 오류를 빠르게 찾아낼 수 있다.

결론
    1. dmypy = mypy를 빠르게 실행하기 위한 데몬 모드 도구
    2. 타입 검사 도구 mypy의 성능을 개선하는 역할
    3. 활용 방법: 서버 실행 → 검사 요청 → 상태 확인 → 종료
    4. 효과: 대규모 프로젝트에서도 타입 검사를 빠르고 효율적으로 수행할 수 있음

1. classmethod
    정의: 클래스 자체를 첫 번째 인자로 받는 메서드이다. 일반 메서드(def method(self))는 객체를 기준으로 동작하지만,
         classmethod는 클래스 자체를 기준으로 동작한다.

    활용 목적
        클래스 단위 로직을 구현할 때 사용
        객체를 생성하지 않고 클래스 자체를 이용한 메서드 호출이 가능

    사용 방법
        @classmethod 데코레이터를 붙여 정의
        첫 번째 매개변수 이름은 관례적으로 cls를 사용

    예시:
        class User:
            count = 0

            def __init__(self, name):
                self.name = name
                User.count += 1

            @classmethod
            def user_count(cls):
                return f"총 사용자 수: {cls.count}"

        # 객체 생성
        u1 = User("철수")
        u2 = User("영희")

        # 클래스 메서드 호출
        print(User.user_count())  # 출력: 총 사용자 수: 2

        -> user_count는 클래스 단위 정보(User.count) 를 다루므로 classmethod로 정의

2. 바다코끼리 연산자
    정의: 할당 표현식이라고 불리며, 변수를 선언하고 값을 할당하면서 동시에 조건문이나 표현식 안에서 사용할 수 있는 연산자이다.
         모양이 바다코끼리(:=)를 닮아서 바다코끼리 연산자라고 부른다.

    활용목적
        중복 계산을 줄이고, 조건문 또는 반복문 안에서 값을 재사용이 가능하다 -> 코드가 간결해진다.

    예시1
        if (n := len("hello")) > 3:
        print(f"문자 길이: {n}")
         -> len("hello")를 두 번 계산할 필요 없이, n에 할당하고 바로 조건식과 출력에서 재사용

    예시2
        data = ["apple", "banana", "", "cherry"]

        while (item := data.pop(0)):
            print(item)
                -> pop(0) 결과를 item에 할당하면서 동시에 반복 조건에 활용

결론
    classmethod: 객체가 아닌 클래스 자체와 관련된 동작을 정의할 때 사용. 주로 클래스 변수를 다루거나, 객체 생성 로직을 클래스 단위로 정의할 때 유용하다.

    바다코끼리 연산자(:=): 변수에 값을 할당하면서 동시에 조건식이나 표현식 안에서 활용할 수 있어 중복 계산을 줄이고 코드 가독성을 높이는 기능이다.

1. TDD란?
    TDD(Test Driven Development) 는 테스트 주도 개발을 의미한다.
    기능을 먼저 개발하는 것이 아니라 테스트 코드를 먼저 작성한 뒤 해당 테스트가 통과하도록 코드를 구현하는 개발 방식이다.

2. TDD 구현 방식(3단계 싸이클)
    (1) Red (실패하는 테스트 작성)
        원하는 기능을 검증하는 테스트 코드를 먼저 작성한다.
        아직 기능이 없으므로 테스트는 실패한다. (의도적으로 실패하도록 한다.)

    (2) Green (기능 코드 작성)
        테스트가 통과할 수 있도록 최소한의 기능 코드를 작성한다.
        이 단계에서 복잡한 최적화보다는 테스트를 통과하는 데 집중한다.

    (3) Refactor (코드 개선)
        기능은 그대로 두고, 코드 구조를 개선하거나 중복을 제거한다.
        개선 후에도 모든 테스트가 통과해야 한다.

    -> 각 기능들마다 위의 과정을 반복하여 기능을 확장해간다.

3. TDD 활용 예
    (1) Red (실패하는 테스트 작성) 예시
        # test_OZ.py
        from calc import add

        def test_add():
            assert add(2, 3) == 5

    -> add 함수가 아직 구현되지 않았으므로 테스트는 실패한다.

    (2) 기능 코드 작성 (Green) 예시
        # OZ.py
        def add(x, y):
            return x + y

    -> 이제 테스트를 실행하면 통과한다. (./test.sh 명령어를 사용했음)


4. TDD의 활용 효과
    (1) 기능이 정확히 동작하는지 즉시 확인 가능

    (2) 버그를 조기에 발견할 수 있음

    (3) 코드 수정·리팩터링 시 안전망 역할 수행

    (4) 협업 시 기능 동작을 문서처럼 공유할 수 있음

5. 결론
    TDD는 “테스트를 먼저 작성하고, 그 테스트를 통과하도록 코드를 구현하는 방식”이고, 구현 방식은 Red → Green → Refactor 3단계를 반복한다.
    활용 효과는 안정적인 코드 작성, 버그 최소화, 협업 효율 증가 등이 있다.

1. Service Design Pattern이란?
    애플리케이션에서 비즈니스 로직(핵심 기능) 을 서비스(Service) 계층으로 분리해 관리하는 설계 방식이다.
    Controller는 요청을 받아 전달만 하고, Service는 실제 로직을 처리하며, Repository/DAO는 데이터베이스와 통신한다.

        -> 이렇게 역할을 분리하면 코드가 명확해지고 유지보수가 쉬워진다.

    Controller (또는 Router): 클라이언트 요청을 받아 서비스 계층에 전달하고, 응답을 돌려주는 역할을 한다.
    Service: 비즈니스 로직을 처리하는 핵심 계층 (예: 회원 가입, 결제 처리 등이 있다.)
    Repository (또는 DAO): 데이터베이스와 직접 연결되어 데이터를 저장·조회·수정하는 계층

        -> 서비스(Service) 계층에 로직을 집중시키고, 다른 계층은 역할만 수행한다는 점이다.

2. Service Design Pattern 활용 예시
    (1) Controller (FastAPI Router)

            from fastapi import APIRouter, Depends
            from services.user_service import UserService
            from schemas import UserCreate

            router = APIRouter()
            user_service = UserService()

            @router.post("/users/")
            def create_user(user: UserCreate):
                return user_service.create_user(user)

            -> Controller는 요청을 받고 서비스에 전달만 한다.

    (2) Service (비즈니스 로직)

            from repositories.user_repository import UserRepository
            from schemas import UserCreate

            class UserService:
                def __init__(self):
                    self.user_repo = UserRepository()

                def create_user(self, user: UserCreate):
                    # 비즈니스 로직 예: 중복 확인 후 저장
                    if self.user_repo.exists(user.name):
                        return {"error": "이미 존재하는 사용자"}
                    return self.user_repo.save(user)

            -> Service는 실제 로직(중복 검사, 규칙 적용 등) 을 처리한다.

    (3) Repository (데이터 처리)

            from schemas import UserCreate

            class UserRepository:
                _db = []

                def save(self, user: UserCreate):
                    self._db.append(user)
                    return {"message": f"{user.name} 등록 완료"}

                def exists(self, name: str) -> bool:
                    return any(u.name == name for u in self._db)

            -> Repository는 데이터 저장/조회 만 담당한다.

3. Service Design Pattern의 장점
    (1) 관심사 분리: Controller, Service, Repository가 각자 역할만 담당

    (2) 재사용성: 서비스 로직을 여러 곳에서 재사용 가능

    (3) 테스트 용이성: 서비스 계층만 따로 테스트 가능 → TDD와도 잘 맞음

    (4) 유지보수성: 기능이 커져도 구조가 명확하여 수정이 쉬움

4. 결론
    Service Design Pattern은 애플리케이션의 비즈니스 로직을 서비스 계층으로 분리하는 설계 방식이다.

    구조: Controller(요청 처리) → Service(로직 처리) → Repository(데이터 처리)

    활용 효과: 코드의 명확성, 유지보수성, 재사용성, 테스트 용이성을 높여준다.

1. Repository Design Pattern이란?
    Repository Design Pattern은 데이터베이스와 직접 연결하는 코드를 분리해서, 데이터 접근(저장·조회·수정·삭제)만 전담하는
    계층(Repository)을 따로 두는 설계 방식이다.

    이 패턴의 목적은 비즈니스 로직(Service) 과 데이터 처리 코드(DB 연결) 를 분리하여 코드의 가독성과 유지보수성을 높이는 것이다.

    -> Repository는 데이터 처리만 담당하고, Service는 비즈니스 로직만 담당한다.

2. Repository Design Pattern 활용 예시
    (1) Controller (FastAPI Router)

            from fastapi import APIRouter
            from services.user_service import UserService
            from schemas import UserCreate

            router = APIRouter()
            user_service = UserService()

            @router.post("/users/")
            def create_user(user: UserCreate):
                return user_service.create_user(user)

            -> Controller는 요청을 받아 Service 계층에 전달.

    (2) Service (비즈니스 로직)

            from repositories.user_repository import UserRepository
            from schemas import UserCreate

            class UserService:
                def __init__(self):
                    self.user_repo = UserRepository()

                def create_user(self, user: UserCreate):
                    if self.user_repo.exists(user.name):
                        return {"error": "이미 존재하는 사용자"}
                    return self.user_repo.save(user)

            -> Service는 중복 확인 같은 비즈니스 규칙 처리 후 Repository에 저장을 요청.

    (3) Repository (데이터 처리)

            from schemas import UserCreate

            class UserRepository:
                _db = []  # 예시용 메모리 DB

                def save(self, user: UserCreate):
                    self._db.append(user)
                    return {"message": f"{user.name} 등록 완료"}

                def exists(self, name: str) -> bool:
                    return any(u.name == name for u in self._db)

                -> Repository는 데이터 저장·조회 같은 DB 처리만 전담.

3. Repository Design Pattern의 장점
    (1) 관심사 분리: 데이터 처리와 비즈니스 로직을 명확히 나눔

    (2) 유지보수성 향상: DB 구조가 바뀌어도 Service 코드 수정이 최소화됨

    (3) 재사용성: Repository를 여러 Service에서 공통으로 활용 가능

    (4) 테스트 용이성: DB를 가짜(Mock)로 대체해 Service만 테스트 가능

4. 결론
    Repository Design Pattern은 데이터 처리 전담 계층(Repository)을 두어 Service와 Controller에서 데이터 접근 코드를 분리하는 설계 방식이다.

    구조: Controller → Service → Repository

    활용 효과: 코드의 명확성, 유지보수성, 테스트 용이성 향상

5, Service Design Pattern, Repository Design Pattern의 차이
    -> Repository Design Pattern과 Service Design Pattern은 둘 다 코드의 역할을 분리하는 설계 방식이지만, 관심사(책임)의 범위가 다릅니다.

    핵심 역할
        Repository Design Pattern
            -> 데이터 접근 전담 / DB 저장·조회·수정·삭제를 처리

        Service Design Pattern
            -> 비즈니스 로직 전담 / 요청 받은 기능을 처리하고 규칙 적용

    위치
        Repository Design Pattern
            -> 데이터 계층 (DB와 직접 연결)

        Service Design Pattern
            -> 서비스 계층 (Controller와 Repository 사이)

    주요 관심사
        Repository Design Pattern
            -> “데이터를 어떻게 다룰 것인가?”

        Service Design Pattern
            -> “비즈니스 요구사항을 어떻게 처리할 것인가?”

    Controller와 관계
        Repository Design Pattern
            -> Controller가 직접 Repository를 호출하는 경우는 거의 없음 → 보통 Service를 통해 사용

        Service Design Pattern
            -> Controller가 Service를 호출해 기능 실행

    예시 기능
        Repository Design Pattern
            -> 유저 정보 DB 저장
            -> 특정 이름 존재 여부 확인

        Service Design Pattern
            -> 회원 가입 시 중복 체크
            -> 결제 시 할인 규칙 적용

    장점
        Repository Design Pattern
            -> 데이터 접근 코드 재사용 가능
            -> DB 구조 변경 시 영향 최소화

        Service Design Pattern
            -> 로직과 데이터 분리
            -> 코드 가독성, 유지보수성, 테스트 용이

    결과
        Repository Design Pattern
            -> 데이터를 안정적으로 다루는 것에 집중

        Service Design Pattern
            -> 애플리케이션의 동작 흐름과 규칙을 책임짐

    정리
        Repository Pattern: 데이터 처리 전담 (DB 다루는 코드만 모음).

        Service Pattern: 비즈니스 로직 전담 (규칙과 기능 처리).

        두 패턴은 보통 함께 사용되며, Controller → Service → Repository → Database 구조로 있다.

------------------------------------------------------------------------------------------------

1. DTO란?
    데이터를 전달(Transfer)하기 위한 객체(Object) 이다.
    주로 클라이언트 ↔ 서버 혹은 계층 간(Controller ↔ Service ↔ Repository) 데이터를 주고받을 때 사용된다.
    핵심 목적은 데이터 형식을 명확히 하고, 불필요한 데이터를 제거해 안전하게 전달하는 것이다.

2. DTO를 사용하는 이유
    (1) 데이터 명확성: 어떤 데이터가 오고 가는지 구조가 분명해짐

    (2) 보안성: 꼭 필요한 데이터만 전달하여 불필요한 노출 방지

    (3) 유지보수성: 데이터 구조가 바뀌어도 DTO를 통해 안정적으로 관리 가능

    (4) 검증 기능: 잘못된 데이터가 들어오는 것을 막을 수 있음 (예: 나이가 음수인지 검사)

3. DTO 활용 예시
    (1) DTO 정의

            from pydantic import BaseModel

            class UserCreateDTO(BaseModel):
                name: str
                age: int

            -> 회원 가입 요청 시 필요한 데이터 형식 정의 (이름, 나이만 받음).

    (2) Router에서 활용

            from fastapi import APIRouter
            from dto import UserCreateDTO

            router = APIRouter()

            @router.post("/users/")
            def create_user(user: UserCreateDTO):
                return {"message": f"{user.name}님이 등록되었습니다.", "age": user.age}

            -> 요청 시 클라이언트가 DTO 형식대로 데이터를 보내야 함.

    (3) 클라이언트 요청 예시
            POST /users/
            {
              "name": "철수",
              "age": 20
            }

            -> DTO에 맞지 않는 데이터(예: age에 문자열 전달)는 자동으로 검증에서 걸러짐.

4. 장점
    (1) 데이터 전달 전용 객체로, 불필요한 데이터 차단

    (2) 데이터 형식 강제 → 잘못된 값 방지

    (3) 각 계층 간 데이터 이동을 단순화 → 협업 및 유지보수에 용이

5. 결론
    DTO(Data Transfer Object) 는 데이터 전달만을 위한 객체이며, 클라이언트와 서버, 계층 간 데이터 교환 시 사용된다.
    FastAPI에서는 보통 Pydantic 모델로 DTO를 정의한다.
    활용 효과: 명확한 데이터 구조, 보안 강화, 유지보수 용이성, 자동 검증.
